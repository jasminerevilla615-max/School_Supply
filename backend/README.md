# Backend setup

The backend uses MySQL. Start MySQL (for example, through XAMPP) before starting Flask. On startup, the application creates the configured database and ORM tables if the MySQL account has `CREATE` privileges.

The backend loads these variables from the repository-root `.env` file. These are the names it reads:

```text
DB_HOST=127.0.0.1
DB_PORT=3306
DB_USER=root
DB_PASSWORD=your-password
DB_NAME=my_school_supply_db
```

Set `SCHOOL_SUPPLY_SECRET` in `.env` to provide the Flask session-signing key. If it is unset, the application creates and reuses a private `.flask_secret` file in the project root so sessions remain valid across server restarts.

The application creates the ORM tables, indexes, standard categories, and the initial administrator account on startup. The administrator is created only when `admin@gmail.com` is absent; later startups preserve that account's profile, password, role, and activation status. Staff accounts are created by an authenticated administrator through User Management; startup does not create a demo staff account. Customer self-registration is limited to 500 customer accounts, enforced by the backend. Existing product and account data is preserved. See the frontend README for development and production run commands.

The initial administrator password is `admin` for development only. Change it after the first sign-in using the administrator profile page.

## System settings

The administrator Settings screen uses the existing authenticated-session data for the account name, username, and email. Password changes reuse the existing administrator password endpoint and user records. Date format, theme, and notification-display preferences are stored in the browser; notification switches filter low-stock and customer-order notifications in the admin interface and do not change server-side notification creation. The Settings screen adds no database tables or API endpoints for these preferences.

## Product catalog and notifications

Admin product creation uses `POST /api/products` with multipart form fields for `name`, `description`, `category_id`, `product_code`, `price`, `unit_cost`, `stock`, `reorder_level`, `status`, and `image`. Product codes are unique and existing products receive `SKU-<id>` codes during the startup migration. The server validates the values and saves the image under `frontend/public/product-images`. It creates the product, inventory row, and per-recipient notifications together in one database transaction. Product management supports searchable, sortable, filterable pages in the Admin interface, with newest products shown first.

`GET /api/products` returns all products to Admin and Staff and active products to Customers. Staff catalog entries identify inactive products as unavailable for sale. Placing an order locks the affected product and inventory records, validates current stock, and decrements product and inventory quantities within the same transaction. The startup migration adds `orders.stock_reserved` with a false default so historical orders are not mistakenly restocked; canceling or rejecting a newly reserved order returns its stock once, while completed orders cannot be cancelled. Notifications are available to the signed-in user at `GET /api/notifications`; `PATCH /api/notifications/<id>/read` marks only that user's notification as read, and `PATCH /api/notifications/read-all` marks only that user's notifications as read. Staff and active customers receive one persisted notification per product. Customers are notified only for active products. Admin notifications are recorded for new customer orders and inventory changes; low-stock alerts use a product's reorder level when configured, otherwise the saved global inventory threshold (5 by default), and the daily report notification is created once per day when Admin notifications are loaded. The low-stock notification preference can disable low-stock notifications. Dashboard clients poll for updates every 15 seconds. Supplier purchase orders are not currently represented in the database, so supplier status notifications are not generated.

Customer notifications are persisted in the existing MySQL `notifications` table. Registration creates one welcome notification; successful customer orders create an order-placed notification; changes to an order's status create a customer notification, including a supplied rejection or cancellation reason when present; and customer display-name, profile-photo, email, and password changes create account notifications. Customers can filter, mark as read, mark all as read, and delete only their own notifications through the customer dashboard.

## Customer checkout and order tracking

Checkout currently supports **Cash on Pickup** only. Customers review current catalog prices, enter their full name, contact email, Philippine mobile number, and complete pickup address, then select this method before submitting. `POST /api/orders` accepts product IDs and quantities, `customer_info`, the `cash_on_pickup` method, and a client-generated idempotency key. The server validates the customer information, recalculates prices and totals, locks and validates stock, reserves inventory, saves an order-specific contact/address snapshot, creates the order and initial status-history entry, and adds customer/Admin/Staff notifications in one transaction. Contact number and address are copied to the customer's saved profile only when the customer checks the explicit save option. The cart is cleared by the frontend only after the server confirms the order was saved. Repeating the same checkout request key for the same customer returns the existing order instead of placing it twice.

`GET /api/orders` lists only the signed-in customer's orders for customer accounts; authorized Admin and Staff accounts can review all orders. Customer order cards include product-name, image, quantity, and unit-price previews from existing order items. `GET /api/orders/<id>` returns order items and status history, with customer ownership enforced. Customers may cancel only their own orders while they are still Pending Confirmation and within five minutes of placement through `POST /api/orders/<id>/cancel`; the deadline and status are checked while the order row is locked, and cancellation returns reserved inventory once. Admin and Staff can update valid workflow transitions through `PUT /api/orders/<id>`; rejecting requires a reason. Only Admin and Staff can mark a Ready for Pickup or Out for Delivery order as Completed. Completing a Cash on Pickup order records pickup time and payment as Paid in the same transaction, after staff confirms collection and cash payment. The customer order-detail view shows known status timestamps; older orders without saved history display only their current status and known order date rather than fabricated steps.

Order and payment statuses remain separate until pickup. New orders start as `Pending Confirmation` and payments start as `Unpaid`; only Admin or Staff can complete an order, and marking a Cash on Pickup order `Completed` records it as Paid after staff confirms that the customer collected the order and paid in cash. Staff confirmation or preparation alone never marks payment as paid. The startup migration adds payment, rejection, idempotency, stock-reservation, receipt-time, checkout contact snapshot, and optional saved customer contact fields to existing tables without deleting historical order data. Staff order cards show the saved order contact email, click-to-call number, and complete address; historical orders without checkout snapshots retain their existing account-name/email fallback.

Customers can submit one 1–5-star review per product per order using `POST /api/orders/<id>/feedback`; the backend requires that the customer owns the order, the order is Completed by Admin or Staff, and the product appears in that order. Reviews are persisted in the `product_feedback` table, with a unique order/product constraint. The existing feedback model stores product ratings and written reviews; it has no separate service-feedback field. `GET /api/products/<id>/reviews` returns actual reviews and `GET /api/product-feedback` is restricted to Admin and Staff. Product listings include review averages/counts. Admin and Staff can view but cannot edit submitted feedback. Customer feedback submission and Staff order-status updates create persisted customer notifications.

## Administrator profile

The admin dashboard profile page uses the authenticated-session endpoints `GET/PUT /api/admin/profile`, `POST /api/admin/profile/password`, and `GET /api/admin/profile/activity`. All endpoints enforce the existing admin role on the server and identify the account from the session; profile updates cannot change a role or account ID. Password changes verify the current password and use the existing Werkzeug password hashing. Profile and password-change activity is recorded in the existing activity log. The admin profile screen does not expose a profile photo or password-change timestamp.

## Staff account profile

The Staff dashboard account menu links to the existing Staff profile, settings, and activity views. Staff-only endpoints under `/api/staff/profile` read and update the signed-in staff member's existing `users` row; requests do not accept a user ID, and profile responses never include password data. Profile fields use the existing name, username, email, contact number, and profile-image columns. Password changes verify the current password, use Werkzeug hashing, advance the account authentication version, and end other active sessions. Recent sign-in and sign-out sessions come from the existing `user_sessions` table and are scoped to the current staff user. Profile photos accept decoded JPG, PNG, and WEBP images up to 5 MB and use generated filenames in `frontend/public/staff-uploads`. The appearance preference reuses the existing browser-stored theme setting. No database tables or schema changes are introduced.

## Customer account profile

The customer account page uses authenticated customer-only endpoints under `/api/customer/profile` for loading and changing a display name, email address, profile photo, and password. Email changes require the current password and a unique address; email verification is not configured, so the API and interface explicitly state that changed addresses are not independently verified. Password changes use Werkzeug hashing, require the current password, and advance a per-user authentication version so other previously signed-in browser sessions are rejected. Profile images accept decoded JPG, PNG, and WEBP files up to 5 MB, are re-encoded with Pillow, and are saved under `frontend/public/customer-uploads` using generated filenames. The users table is migrated at startup with nullable `profile_image_url` and a zero-defaulted `auth_version`; Admin Customer Management reads these same user records and refreshes the list periodically.
